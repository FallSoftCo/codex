Codex capabilities overlapping Losangelex and Hollywood
======================================================

Comparison: upstream `44d76c6a6dd04fa2efc302b906ac8774267a1272` (July 23, 2026), the legacy fork's merge base, to `f8ab57359dde6b6d5de1aee613c18fe60b661aeb` (September 10). Dates below are upstream commit dates. This is a source and test inspection, not a claim that every feature is enabled in every distributed client or has been exercised in Losangelex.

Losangelex already used app-server for interactive peer sessions, Hollywood attachment, and inbound room delivery. Adopting app-server is not the proposed change. The question is which upstream capabilities now replace parts of that integration.

**Already present in July.** The baseline contains `spawn_agent`, `send_message`, `followup_task`, `interrupt_agent`, `list_agents`, and `wait_agent`, with a registry shared inside each root agent tree. It also contains the context, turn-input, and thread-lifecycle extension interfaces. These are visible in the [July tool implementation](https://github.com/openai/codex/blob/44d76c6a6dd04fa2efc302b906ac8774267a1272/codex-rs/core/src/tools/handlers/multi_agents_v2.rs) and [July extension API](https://github.com/openai/codex/blob/44d76c6a6dd04fa2efc302b906ac8774267a1272/codex-rs/ext/extension-api/src/contributors.rs).

The merge-base commit itself is [Wake sleeping threads for queued agent mail](https://github.com/openai/codex/commit/44d76c6a6dd04fa2efc302b906ac8774267a1272). It lets pending mailbox messages wake an outstanding durable sleep even when the message does not request a new turn. An ordinary idle thread still requires a turn-triggering message. Inboxes and this wake distinction were already part of July's upstream baseline.

**Boundaries that affect the design.**

- The collaboration registry is still scoped to one root's agent tree: [AgentControl](../codex-rs/core/src/agent/control.rs). V2 messaging validates registry membership; `followup_task` rejects the root as its target. A shared dashboard can show multiple roots without turning them into a shared peer-message room.
- V2 children remain parent-owned. August 24 tightened direct app-server mutation checks across their input surfaces: [ownership enforcement](https://github.com/openai/codex/commit/b6333bb1bb). Use independent roots for peers the human must steer independently.
- Three mechanisms have different contracts: the runtime agent mailbox, the durable **user-submission** queue, and externally supplied **tool-authority** content. The current mailbox uses an in-memory deque; the persistent queue accepts user submissions. Neither observation establishes durable cross-room delivery of arbitrary peer messages. See [input queue](../codex-rs/core/src/session/input_queue.rs), [queue extension](../codex-rs/ext/queue/src/service.rs), and [ExternalMessage](../sdk/python/docs/api-reference.md#externalmessage).
- `ExternalMessage` starts an idle turn. Hollywood must still decide whether traffic is a required obligation or optional context before delivery. The API does not supply room membership, authenticated peer identity, a durable room cursor, or cross-service deduplication. Tool name and namespace are labels, not identity proof.
- Restart recovery uses cold resume. Shutdown persistence excludes ephemeral and non-root threads; forced shutdown need not produce a recovery snapshot. The managed path does not preserve an in-flight model request or shell process merely by restoring a thread. Manual updates can still interrupt work: [daemon contract](../codex-rs/app-server-daemon/README.md).
- At this pinned commit, `multi_agent` defaults on and `multi_agent_v2` defaults off despite being marked stable. Queue RPCs are experimental. Compare an explicitly configured v2 baseline as well as the default product: [feature registry](../codex-rs/features/src/lib.rs).

**What Hollywood still contributes.** No built-in equivalent to the complete Hollywood room-and-coordination contract was found in the inspected upstream surfaces. The remaining product is persistent rooms across independent roots and app-server instances; named peer membership; addressed messages and required obligations; a shared task board and ownership; path claims and leases; and room policy, phase, epoch, and leader/verifier state. Existing implementations still need failure testing before their guarantees are carried forward. The legacy [product description](https://github.com/FallSoftCo/codex/blob/468b24abd9549dece2e7a92e6353ea4d4bc43778/README.md) identifies these surfaces.

Interactive session management, generic inboxes, subagent execution, and basic reconnect now have substantial upstream coverage. Those alone do not establish a reason for the fork to exist or evidence that it outperforms Codex.

**Effect on the renewal plan.** Keep the current upstream runtime and dashboard. First test a Hollywood service adapter that uses existing app-server events, external-message input, and coordination tools. Retain Hollywood's durable admission and delivery state. Add an internal extension only when a concrete requirement, such as passive bounded room context or a lifecycle hook, cannot be met through the public API. This is a feasibility recommendation, not a completed or validated replacement of the native integration.

Replay the July no-op wake and required-obligation failures against that candidate with the actual model. Also verify delivery after disconnection and restart, duplicate suppression, user steering, ownership enforcement, and silence after completion. Existing native reconnect and daemon recovery should be the starting point for development continuity; separately installed daily and candidate packages prevent development builds from changing the daily runtime in the first place.
